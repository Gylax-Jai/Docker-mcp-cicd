================================================================================
                    CI/CD & GIT COLLABORATION HANDBOOK
================================================================================

CI/CD is a way teams automate getting code from a developer’s laptop into a 
reliable, running product.

* CI (Continuous Integration): Developers merge small changes often. Every change 
  automatically builds the project and runs checks such as tests, linting, and 
  security scans.
* CD (Continuous Delivery / Deployment):
  - Continuous Delivery: Code is always ready to release, but a person approves it.
  - Continuous Deployment: Every passing change is released automatically.

Think of it like an analogy:
CI/CD is the Chef.
The Pipeline (YAML file) is the Recipe Book.

--------------------------------------------------------------------------------
1. THE BASIC FLOW
--------------------------------------------------------------------------------
Write code → Push to Git → Build → Test → Scan → Deploy → Monitor

Example: You change a login button and push it to GitHub. CI automatically:
1. Installs dependencies.
2. Runs unit/integration tests.
3. Builds the app (or Docker images).
4. Checks for vulnerabilities.
5. If everything passes, it deploys it.

Why it matters: It catches problems early, makes releases predictable, reduces 
manual mistakes, and lets teams ship faster.

--------------------------------------------------------------------------------
2. PIPELINE CONCEPTS & VOCABULARY
--------------------------------------------------------------------------------
| Term          | Meaning                                                      |
|---------------|--------------------------------------------------------------|
| Pipeline / CI | The automated sequence of instructions (the workflow).       |
| YAML (.yml)   | The file format used to write the instructions (ci.yml).     |
| Trigger       | The event that starts it (e.g., "on: pull_request").         |
| Runner/Agent  | The temporary cloud machine that executes the steps.         |
| Job & Step    | A Job is a group of Steps. A Step is a single command.       |
| Build Artifact| The output of a build (e.g., a compiled Docker Image).       |
| Environment   | Where it lives (Dev, Staging, Production).                   |
| Secrets       | Hidden, protected API keys/passwords used by the pipeline.   |

--------------------------------------------------------------------------------
3. GIT COLLABORATION BEST PRACTICES
--------------------------------------------------------------------------------
* Never push directly to `main`. Keep `main` stable and protected.
* Use a branch for every feature or fix (e.g., `fix-ci-pipeline`).
* Open a Pull Request (PR) for every merge into `main`.
* Require CI checks to PASS before merging is allowed.

Pull Request vs Git Pull:
* `git pull`: Downloads the latest code to your local computer.
* `Pull Request (PR)`: A formal request on GitHub to merge your branch into main 
  after review and CI testing.

--------------------------------------------------------------------------------
4. MINI PROJECT: GITHUB ACTIONS DOCKER PIPELINE
--------------------------------------------------------------------------------
We built a CI pipeline to test a 3-tier architecture (React + Node + MongoDB).

Workflow File: `.github/workflows/ci.yml`

What the pipeline does on every Pull Request:
1. Rents an Ubuntu server.
2. Checks out the code.
3. Builds the Frontend and Backend Docker Images.
4. Creates an external Docker volume (`favorites-mongo-data`).
5. Runs `docker compose up -d backend mongo`.
6. Waits 10 seconds for the database to boot.
7. Runs `curl` to test the API health.
8. If curl returns data = ✅ PASS. If curl fails = ❌ FAIL (Blocks the merge).
9. Shuts down containers and destroys the server.

This exact workflow ensures that a broken Dockerfile or a crashing backend can 
never be accidentally merged into the main codebase!
