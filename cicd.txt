CI/CD is a way teams automate getting code from a developer’s laptop into a reliable, running product.

- CI — Continuous Integration: developers merge small changes often. Every change automatically builds the project and runs checks such as tests, linting, type checking, and security scans.
- CD — Continuous Delivery / Deployment:
  - Continuous Delivery: code is always ready to release, but a person approves production release.
  - Continuous Deployment: every change that passes the pipeline is released to production automatically.

cicd is basically a  process for automatic testing, building scan and deployment 
while pipeline is an automation workflow written in yml config file which basically 
say if there is any code changes push or pr do these written steps. 
Analogy- cicd is chef and pipeline is recipe book

The basic flow looks like this:
Write code → Push to Git → Build → Test → Scan → Deploy → Monitor
Example: you change a login button, push it to GitHub, and CI automatically:
1. Installs dependencies.
2. Runs unit/integration tests.
3. Builds the app.
4. Checks formatting, types, and known vulnerabilities.
5. If everything passes, deploys it to a preview, staging, or production environment.


Why it matters: it catches problems early, makes releases predictable, reduces manual deployment mistakes, and lets teams ship smaller changes more frequently.
Common pieces:

Popular CI/CD platforms include GitHub Actions, GitLab CI/CD, Jenkins.


What is a pipeline?
A pipeline is an automated sequence of instructions.
It is usually written in a YAML file inside the project. For GitHub Actions, an example location is:
.github/workflows/ci.yml
Example:
name: CI

on:
  pull_request:
  push:
    branches: [main]

jobs:
  test:
    runs-on: ubuntu-latest

    steps:
      - uses: actions/checkout@v4

      - uses: actions/setup-node@v4
        with:
          node-version: 20

      - run: npm ci
      - run: npm test
      - run: npm run build
This says:
When a Pull Request opens or code is pushed to main:
→ start a temporary Linux machine
→ download the code
→ install Node.js
→ install packages
→ run tests
→ build the app

CI/CD does not require Docker
CI/CD works without a Dockerfile or Docker Compose.

Examples:
Node.js:   npm ci → npm test → npm run build
Python:    pip install -r requirements.txt → pytest
Java:      mvn test → mvn package
Static site: build files → deploy to Vercel/Netlify
Docker is optional. It packages an app and its dependencies into a consistent container.
Code → CI tests → build Docker image → push image to registry → deploy container
Docker Compose is mostly useful for local development or integration tests involving multiple services:
App + database + Redis + queue


Git collaboration best practice-:

Keep main stable and protected. Do not directly push normal feature work to main.
main
 ├── feature/login-page
 └── feature/ai-chat

Each developer:
main → personal feature branch → Pull Request → review + CI → merge to main
Example:
git switch main
git pull origin main
git switch -c feature/login-page

# Make changes
git add .
git commit -m "Add login page"
git push -u origin feature/login-page
Then open a Pull Request:
feature/login-page → main


Pull Request vs git pull
They are different.
git pull
= download latest shared code into your computer

Pull Request (PR)
= request to merge your branch into main on GitHub
A PR is where the team reviews the code and CI runs checks before merging.
If two people work at the same time
You work on feature/login-page.
Your friend works on feature/ai-chat.
Both open separate Pull Requests.
If your friend’s PR merges first, their code goes into main. Your PR remains open. Before merging yours, update your branch with the latest main:
git switch feature/login-page
git fetch origin
git merge origin/main
git push
Meaning:
git switch feature/login-page
= move to your branch

git fetch origin
= download the latest GitHub information, without changing files

git merge origin/main
= combine the latest main changes into your current branch

git push
= upload your updated branch to GitHub
GitHub updates your PR and runs CI again.


Merge conflicts
A merge conflict occurs when two people change the same nearby lines differently and Git cannot decide which version is correct.
Example:
// Original
const appName = "Project A";
You change it:
const appName = "Project A Web";
Your friend changes it:
const appName = "AI Project A";
Git asks a human to choose or combine the final version. After fixing it:
git add .
git commit -m "Resolve merge conflict"
git push
Conflicts usually do not happen if people edit different files or different parts of a file.


Best team rules
- Use a branch for every feature, fix, or task.
- Never normally push directly to main.
- Open a Pull Request for every merge into main.
- Require CI checks to pass before merging.
- Keep PRs small and focused.
- Update your branch from main before merging if someone else merged first.
- Communicate before two people change the same large file or feature.
- Use clear branch names: feature/login, fix/cart-total, chore/update-dependencies.
- Use clear commit messages: Add login validation, Fix broken checkout redirect.
- Store API keys and passwords as CI/CD secrets—never commit them into code.
Recommended branch protection for main
Configure GitHub so that main requires:
- A Pull Request
- Passing CI checks
- At least one review approval (for teams)
- No unresolved merge conflicts

Mini CI/CD Activity
Use your existing project with:

frontend + backend + MongoDB + Docker + Docker Compose
Your goal is to make GitHub automatically check that your project can build and start correctly.
Steps
1. Push your existing project to GitHub on the main branch.
2. Create a new branch for the CI work:
git switch -c ci/docker-build
3. In the top-level project folder, create:
.github/workflows/ci.yml
4. In ci.yml, write instructions for GitHub:
When I push code or open a Pull Request:
1. Build the frontend Docker image.
2. Build the backend Docker image.
3. Start MongoDB and the backend.
4. Check whether backend `/health` is working.
5. Mark the pipeline successful if everything works.
6. Push this branch to GitHub:
git add .
git commit -m "Add CI workflow"
git push -u origin ci/docker-build
6. On GitHub, open a Pull Request:
ci/docker-build → main
7. Go to the GitHub Actions tab and watch the workflow run.
Green ✅ = Docker images built and backend started successfully
Red ❌ = something failed; read the logs and fix it

8. Make one small intentional mistake, such as breaking the backend Dockerfile or /health route. Push it and see CI fail.
9. Fix the mistake, push again, and see CI pass.
10. Merge the Pull Request into main.

What you learn

Push / Pull Request triggers CI
CI runs on GitHub’s machine
Docker build is tested automatically
A failed check blocks safe merging
Logs help find the problem
A successful PR can be merged into main
This is your first real CI project.

4. MINI PROJECT: GITHUB ACTIONS DOCKER PIPELINE
--------------------------------------------------------------------------------
We built a CI pipeline to test a 3-tier architecture (React + Node + MongoDB).

Workflow File: `.github/workflows/ci.yml`

What the pipeline does on every Pull Request:
1. Rents an Ubuntu server.
2. Checks out the code.
3. Builds the Frontend and Backend Docker Images.
4. Creates an external Docker volume (`favorites-mongo-data`).
5. Runs `docker compose up -d backend mongo`.
6. Waits 10 seconds for the database to boot.
7. Runs `curl` to test the API health.
8. If curl returns data = ✅ PASS. If curl fails = ❌ FAIL (Blocks the merge).
9. Shuts down containers and destroys the server.

This exact workflow ensures that a broken Dockerfile or a crashing backend can 
never be accidentally merged into the main codebase!
